# Ontology-Grounded Project Memory for Coding Agents

Spotlight：这篇论文不是在做更大模型，而是把“软件工程中的知识保真”变成可编程基础设施，把代码代理的上下文记忆从向量检索升级到有生命周期和因果关系的图谱检索。

## 论文内容
- 核心问题：代码代理在高频变更中难以追踪“为什么这样改”，缺乏可维护、可追溯、可否决的结构化记忆，导致决策漂移和上下文断裂。
- 方法概要：提出 MOOSEDev，用知识图谱承载架构决策、经验教训、约束条件与推理依据；通过 MCP 暴露给代理。记录保留生命周期、来源、取代关系等元信息，并由 MOOSE neurosymbolic 引擎做查询和推理。
- 主要贡献：
  - 将“项目记忆”从非结构化检索升级为“可解释知识图谱”与符号推理通道。
  - 明确定义 supersession / set-completeness / negation 三类关键问答场景，便于可控对齐。
  - 给出公开基线对比：在 835 条类型化记录上实现近似完整召回（0.98–1.00）而传统向量 top-k 多停留在 6%–27%。
- 关键实验或结果：
  - 相对于生产级向量记忆工具，超集/补充性与否定查询上覆盖率显著提升。
  - 在这两类关键查询上 MOOSEDev 覆盖率接近满分，且相关性回撤和 token 成本与对比系统基本持平（按论文摘要叙述）。
- 适合关注的原因：
  - 代理编码场景里，正确调用 API 之外更难的是“记住以前为什么这么做”，该方法直击工程可落地痛点。
  - 与 LLM coding agent 与代码库治理结合后，可显著降低“历史知识丢失”导致的返工。
- 局限性或待验证点：
  - 当前结果主要来自公开语料与自建基线对比，真实超大型企业代码库中的实时更新压力尚需验证。
  - 符号图谱维护开销和入库策略会影响系统可扩展性，需要工程上进一步量化。
- 对后续研究/应用的启发：
  - 可以将该记忆结构与自动代码审查、变更原因追踪、测试失败归因联动，形成“记忆-决策-验证”闭环。
  - 对多代理协作（编译、测试、重构）尤其适合做共享记忆层。
- Obsidian 快速浏览一句总结：**比把历史嵌到上下文窗口里更关键的是，先有一套能追责的知识结构让代理知道“该记什么”。**

## 标准化研究框架
**Research question：** 在高频代码变更场景中，基于本体和符号图谱的项目记忆是否能比单纯向量检索更好地支持 coding agent 的可复用决策？

**Literature：** 现有 coding agent 研究多关注模型行为生成与工具调用，较少对“组织级记忆”进行结构化建模；此工作将记忆工程化并与 MCP 接口绑定，处于方法论交叉点。

**Theory：** 软件演化本质是“结构化因果链”积累：决策-原因-后果需要显式连接。符号化记忆可提供可校验上下文，减少仅基于相似度检索的捷径推断。

**Hypotheses：**  
- H1：面向项目决策的知识图谱检索在完整性与反证查询上优于向量检索。  
- H2：将生命周期与取代关系引入记忆表示可降低错误复用与重复决策。  
- H3：在检索质量提升的同时，不会显著增加相关性与 token 成本。

**Method：** 使用 MOOSEDev 构建 typed records 的项目图谱（含 lifecycle/provenance/supersession 元数据），通过 MCP 接口向代理暴露查询；对照 835 条记录测试三类问题集。

**Data and Analysis：** 采用公开中性语料与代码历史进行中性测试；比较 MOOSEDev 与生产向量记忆在 expected answer set 上的覆盖率、取代链一致性以及成本指标。

**Findings：** 摘要报告显示，在关键问答任务上检索完整性更高，而相关性与 token 消耗未显著走输基线，验证了结构化记忆可在工程代价内提升稳健性。

**Conclusion：** 论文支持“编码 agent 记忆层优先于更大模型”这一方向：符号化项目记忆可作为 LLM 代理稳定性和可审计性的重要基础设施。
