## 核心问题

LLM 可能编造工具名、参数或参数类型。多台 MCP server 合并目录时，还会出现同名冲突、遮蔽和来源混淆。仅检查任务授权不足以保证调用引用有效。

## 方法概要

Resolution Rung 根据可信注册表检查名称和签名，再交给后续权限层；MCP 版本把引用解析到 server 与 tool 的组合。该方法无需模型训练，但不能识别所有“参数格式合法、语义却选错工具”的情况。见正文 §II–V、§VII。

## 主要贡献

给出单注册表与多服务器错误分类、两个调用界面的实测，以及一个可作为对照的最小解析器。作者明确不把注册表查询和类型检查本身称为新算法；应重点评价测量与边界说明。

## 关键实验或结果

正文 §VI–VII：10 个托管模型在单注册表实验产生 322 次幻觉调用，MCP 界面产生 154 次。解析器拦截这些可检出的调用，但 fail-open 对照“全部执行”以及部分零错误结果是构造假设下的结果，并非生产系统被实际攻破的比例。不能把调用计数解释为总体真实业务发生率。

## 适合关注的原因

适合设计工具路由、MCP host 或 Agent 评测的读者。它把名称解析、参数验证、权限判定和语义选错分开，有助于定位失败究竟属于哪一层。

## 局限性或待验证点

正文 §X 承认，合法调用零误拒来自解析器自己的生成器，不是独立业务语料证据；每个模型每个界面只有 60 次探测，缺少置信区间和随机种子变化。可信注册表也不能覆盖注册表本身被污染。所谓必须先解析的结论依赖文中 gate 接口；严格拒绝未知调用的执行器已实现相关功能，不能笼统断言所有现有框架都缺失防护。

## 对后续研究 / 应用的启发

**笔记分析：** 可用真实合法调用回放测误拒，再注入同名冲突和签名变更测漏检；同时记录错误反馈后 Agent 能否恢复。比单纯统计拦截率更有用的是同时报告任务完成、错误路由和恢复成本。

## Obsidian 快速浏览总结

**一句话：** 工具调用需要先解析再授权，但格式正确仍不意味着语义正确。

## 标准化研究框架

**Research question：** 哪些工具幻觉可以通过执行前解析检测，多服务器合并增加了哪些问题？

**Literature：** 对接工具选择、最小权限与工具契约验证研究，关系见正文 §IX。

**Theory：** 等价于形式化接口与威胁模型：可信、封闭注册表下检查成员与签名；不是社会科学理论。

**Hypotheses：** 等价于测量命题和工程断言：调用界面影响幻觉表现，解析器可拒绝 schema 可识别错误；不构成普适安全保证。

**Method：** 错误分类、接口形式化、真实模型探测及合成消融。

**Data and Analysis：** 区分真实产生的错误计数与执行器构造决定的接受结果，分别讨论单注册表和 MCP。

**Findings：** 能检测引用与签名错误，保留 schema 无法区分的语义混淆。

**Conclusion：** 支持增加明确的解析边界；独立误拒测试和端到端恢复实验仍有必要。
